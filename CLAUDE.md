# GoServe — Project Rules

Read first: `docs/PLAN.md` (the process), `docs/process-trace.md`, and `docs/LEARNINGS.md`.

Standing rules, every session:

1. First action: read `docs/process-trace.md` and `docs/LEARNINGS.md`. Last action before "done": append this session's steps to the trace (one row each: date, step, actor, what, artifact, owner contact asked / volunteered / reviewed), and add one row to `docs/LEARNINGS.md` for every learning or mistake.
2. Every owner message that changes direction gets bullets in `docs/discussions/<START_DATE>.md`.
3. Every idea the owner states is logged at once to `docs/ideas.md`, with status (open / taken / dropped).
4. Work only from GitHub issues. An **Epic is a feature** (issue labelled `epic`). A **user story is a sub-issue** (issue labelled `story`) attached to its correct Epic. Branch `feat/<issue>-<slug>` from `dev`. PR feat → dev (self-review checklist, CI green). PR dev → main at each demo increment. **Two GitHub accounts (owner, 13 Oct 2026):** all development — commits, pushes, opening PRs — happens through the owner's development account (`klickbae8yt-star`); **every review and every merge (feat → dev and dev → main) is done by `satvik-jain-iitd`**. Claude never merges (the temporary docs-only exception ended 13 Oct 2026). Never push directly to `main` or `dev`. **In this folder the active GitHub account is always `klickbae8yt-star`** (git and gh); other projects stay on `satvik-jain-iitd`. **How (no account switching):** this repo's git pushes use `klickbae8yt-star` through a repo-local credential helper (`gh auth token --user klickbae8yt-star`); `gh` commands in this folder use `klickbae8yt-star` automatically (a `gh()` wrapper in `~/.zshrc` sets `GH_TOKEN` when the path is under `~/Documents/GoServe`; if it is not loaded, prefix `GH_TOKEN=$(gh auth token --user klickbae8yt-star)`). Never change the Mac's global active `gh` account (`satvik-jain-iitd`); the owner reviews and merges in the browser.
5. TDD: failing test first, named after the Gherkin scenario, failure pasted in the PR. Each test is linked to its correct user story. The test file is attached to that story's sub-issue. Every test is listed in `docs/tests/test-cases.md`.
6. Ponytail: only the code the story needs. Nothing speculative.
7. Definition of Ready before a story starts; Definition of Done before it closes (see `docs/PLAN.md`).
8. Decisions that change architecture or scope get `docs/decisions/ADR-NNN.md` in the same PR.
9. PWA first. One codebase for customer, kitchen, rider, and ops. Backend does the work. Final stack is fixed by its own ADR.
10. Every assumption goes in `docs/assumptions.md`. Every follow-up goes in `docs/follow-ups.md`. Nothing stays tacit.
11. Before building any feature: create its feature branch first, then write the business-level description, the product-level description, the acceptance criteria, and the docs on that branch.
12. Commits follow `COMMIT_GUIDELINES.md` (Conventional Commits, English, short). PRs stay small: max 50 files (PRs into `main` are releases and skip the file cap). CI must be green before merge.
13. Pre-commit runs on every commit: no secrets, no files over 500KB, no merge markers, markdown code blocks closed, commit message checked.
14. Rollback: if a change breaks something, roll back or fix only the feature branch that caused it. Never touch unrelated branches.
15. No secrets in code. Secrets live in `~/Desktop/Secrets/` and in GitHub Actions secrets. Never commit a `.env`, key, or token.
16. Phase gate: before starting any MVP phase, run `docs/architecture/phase-gate.md` — an AskUserQuestion Q&A with the owner on every infrastructure item for that phase, research where he has nothing, set up with his yes, record in `docs/ARCHITECTURE_COMPONENTS.md`. Nothing in the phase is built until the gate passes.
17. **`main` holds only run-critical code** (owner, 13 Oct 2026): `site/`, `app/`, `scripts/`, `design/tokens.json` + `design/brand/`, `ops/`, `.github/`, `.gitignore`, `README.md`. **Exception: `ops/ai/` (offline tools such as the Laya data generator) stays on `dev`** (reviewer, 22 Oct 2026). No docs, plans, decisions or rules on `main` — they live on `documents`. Promote to `main` with a release branch cut from `main` that takes only those paths from `dev` (or `staging`, see `docs/PLAN.md` §2); never merge `dev` or `staging` into `main` directly.

**Branch map (owner, 26 Oct 2026, plan v2 decision D7):** `main` = releases only. `dev` = the PWA MVP2; after the freeze (tag `mvp2-demo`) it takes hotfixes only, on the owner's ask. `staging` = the native apps and backend v2, **code only** (`supabase/`, `api/`, `android/`, `ios/`, `design/tokens.json`, `.github/`); it follows the same dev practice as `dev` (feature branch, red test first, PR, CI green, owner merges). `documents` = every document: plans, ADRs, research, the phone test list, the trace, learnings and the PR review book. The old `docs/...` feature branches stay; the branch is called `documents` because Git cannot hold both `docs` and `docs/...`.
18. **`letsdwelo.in` is a temporary home** (owner, 13 Oct 2026): the domain belongs to the owner's Dropshipping project (Dwelo e-commerce). It shows only the GoServe investor site (`site/`, Pages project `goserve`). Do not change it, deploy to it, or touch its domain settings unless the owner asks — any change to `site/` on `main` redeploys it. Later, when GoServe has its own domain, the investor site moves there and `letsdwelo.in` goes back to Dwelo (owner's call). The product app is built in `app/` and hosted on its own Pages project `goserve-app` at **`goserve-app.pages.dev`**. No custom domain for the app for now.
19. **One stack open per lane at a time** (owner, 22 Oct 2026; lanes added 26 Oct 2026, plan v2 decision D6). A stack is one PR, or a chain of stacked PRs made with `gh stack` (`gh extension install github/gh-stack`): the bottom PR targets the lane's base branch, each layer above targets the branch below it. The lanes are: `pwa` (base `dev`), `documents` (base `documents`), and on `staging` three lanes fenced by folder: `backend` (`supabase/`, `api/`), `android` (`android/`) and `ios` (`ios/`). One stack may be open in each lane, so Android and iOS can move in parallel; a lane never touches another lane's folder (shared paths such as `design/tokens.json` and `.github/` belong to the lane that opened the open stack on them, and a second lane waits). Before this change the rule was one stack in the whole repo. Work that depends on an open PR goes in a layer on top of it, never in a loose PR. Before every push of a new branch run `gh pr list --state open` (all authors; the Laya session counts); if an open PR in your lane is not yours and not in your stack, wait on a local branch. Each layer is a small story (rule 12 file cap per layer). Each layer carries its own `## For the reviewer` block. The reviewer reviews and approves one layer at a time, bottom first. The owner merges each layer right after its approve block, bottom up; GitHub rebases the layers above and keeps their approvals when the code did not change. A review change is a commit on the same layer; after it, run `gh stack sync` so the layers above follow. Never merge a layer above an unapproved one. The only PRs that may open beside a lane's stack are a release PR the owner asked for and a PR in another lane.

Before any new component, script, skill, workflow or tool in this project: run the `radar` skill (`radar@agi`) on the need, read the top 3 READMEs, record the run in `docs/research/repo-radar.md`, reuse or borrow first. Build from scratch only when the run found nothing, and say so. No radar run, no new code. Full text: `~/.claude/CLAUDE.md` section 2, rule 0.
