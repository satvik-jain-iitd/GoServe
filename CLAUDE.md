# GoServe — Project Rules

Protocol: follow knowledge/shipquick_latest/CLAUDE.md

Read first: `docs/PLAN.md` (the process), `docs/process-trace.md`, and `docs/LEARNINGS.md`.

Standing rules, every session:

1. First action: read `docs/process-trace.md` and `docs/LEARNINGS.md`. Last action before "done": append this session's steps to the trace (one row each: date, step, actor, what, artifact, owner contact asked / volunteered / reviewed), and add one row to `docs/LEARNINGS.md` for every learning or mistake.
2. Every owner message that changes direction gets bullets in `docs/discussions/<START_DATE>.md`.
3. Every idea the owner states is logged at once to `docs/ideas.md`, with status (open / taken / dropped).
4. Work only from GitHub issues. An **Epic is a feature** (issue labelled `epic`). A **user story is a sub-issue** (issue labelled `story`) attached to its correct Epic. Branch `feat/<issue>-<slug>` from `dev`. PR feat → dev (self-review checklist, CI green). PR dev → main at each demo increment. **Two GitHub accounts (owner, 13 Oct 2026):** all development — commits, pushes, opening PRs — happens through the owner's development account (`klickbae8yt-star`); **every review and every merge (feat → dev and dev → main) is done by `satvik-jain-iitd`**. Claude never merges (the temporary docs-only exception ended 13 Oct 2026). Never push directly to `main` or `dev`. **In this folder the active GitHub account is always `klickbae8yt-star`** (git and gh); other projects stay on `satvik-jain-iitd`. **How (no account switching):** this repo's git pushes use `klickbae8yt-star` through a repo-local credential helper (`gh auth token --user klickbae8yt-star`); `gh` commands in this folder use `klickbae8yt-star` automatically (a `gh()` wrapper in `~/.zshrc` sets `GH_TOKEN` when the path is under `~/Documents/GoServe`; if it is not loaded, prefix `GH_TOKEN=$(gh auth token --user klickbae8yt-star)`). Never change the Mac's global active `gh` account (`satvik-jain-iitd`); the owner reviews and merges in the browser.
5. TDD: failing test first, named after the Gherkin scenario, failure pasted in the PR. Each test is linked to its correct user story. The test file is attached to that story's sub-issue. Every test is listed in `docs/tests/test-cases.md`.
6. Ponytail: only the code the story needs. Nothing speculative.
7. Definition of Ready before a story starts; Definition of Done before it closes (see `docs/PLAN.md`).
8. Decisions that change architecture or scope get `docs/decisions/ADR-NNN.md` in the same PR.
9. PWA first. One codebase for customer, kitchen, rider, and ops. Backend does the work. Final stack is fixed by its own ADR.
10. Every assumption goes in `docs/assumptions.md`. Every follow-up goes in `docs/follow-ups.md`. Nothing stays tacit.
11. Before building any feature: create its feature branch first, then write the business-level description, the product-level description, the acceptance criteria, and the docs on that branch.
12. Commits follow `COMMIT_GUIDELINES.md` (Conventional Commits, English, short). PRs stay small: max 50 files (PRs into `main` are releases and skip the file cap). CI must be green before merge.
13. Pre-commit runs on every commit: no secrets, no files over 500KB, no merge markers, markdown code blocks closed, commit message checked.
14. Rollback: if a change breaks something, roll back or fix only the feature branch that caused it. Never touch unrelated branches.
15. No secrets in code. Secrets live in `~/Desktop/Secrets/` and in GitHub Actions secrets. Never commit a `.env`, key, or token.
16. Phase gate: before starting any MVP phase, run `docs/architecture/phase-gate.md` — an AskUserQuestion Q&A with the owner on every infrastructure item for that phase, research where he has nothing, set up with his yes, record in `docs/ARCHITECTURE_COMPONENTS.md`. Nothing in the phase is built until the gate passes.
17. **`main` holds only run-critical code** (owner, 13 Oct 2026): `site/`, `app/`, `scripts/`, `supabase/` and `api/` (the prod edge functions and their contract; owner, 29 Oct 2026, release #774), `design/tokens.json` + `design/brand/`, `ops/`, `.github/`, `.gitignore`, `README.md`. **Exception: `ops/ai/` (offline tools such as the Laya data generator) stays on `dev`** (reviewer, 22 Oct 2026). No docs, plans, decisions or rules on `main` — they live on `documents`. Promote to `main` with a release branch cut from `main` that takes only those paths from `dev` (or `staging`, see `docs/PLAN.md` §2); never merge `dev` or `staging` into `main` directly.

**Branch map (owner, 26 Oct 2026, plan v2 decision D7):** `main` = releases only. `dev` = the PWA MVP2; after the freeze (tag `mvp2-demo`) it takes hotfixes only, on the owner's ask. `staging` = the native apps and backend v2, **code only** (`supabase/`, `api/`, `spec/` for the shared Gherkin, `android/`, `ios/`, `design/tokens.json`, `.github/`); it follows the same dev practice as `dev` (feature branch, red test first, PR, CI green, owner merges). `documents` = every document: plans, ADRs, research, the phone test list, the trace, learnings and the PR review book. `CLAUDE.md` is the one rule file allowed on `staging` and `dev` (so a session there loads these rules); it must stay identical to the copy on `documents`, and the first `staging` PR copies it in. The old `docs/...` feature branches stay; the branch is called `documents` because Git cannot hold both `docs` and `docs/...`.

It shows only the GoServe investor site (`site/`, Pages project `goserve`). 19. **One stack open per lane at a time** (owner, 22 Oct 2026; lanes added 26 Oct 2026, plan v2 decision D6). A stack is one PR, or a chain of stacked PRs made with `gh stack` (`gh extension install github/gh-stack`): the bottom PR targets the lane's base branch, each layer above targets the branch below it. The lanes are: `pwa` (base `dev`), `documents` (base `documents`), and on `staging` three lanes fenced by folder: `backend` (`supabase/`, `api/`, `spec/`), `android` (`android/`) and `ios` (`ios/`). One stack may be open in each lane, so Android and iOS can move in parallel; a lane never touches another lane's folder (shared paths such as `design/tokens.json` and `.github/` belong to the lane that opened the open stack on them, and a second lane waits). Before this change the rule was one stack in the whole repo. Work that depends on an open PR goes in a layer on top of it, never in a loose PR. Before every push of a new branch run `gh pr list --state open` (all authors; the Laya session counts); if an open PR in your lane is not yours and not in your stack, wait on a local branch. Each layer is a small story (rule 12 file cap per layer). Each layer carries its own `## For the reviewer` block. The reviewer reviews and approves one layer at a time, bottom first. The owner merges each layer right after its approve block, bottom up; GitHub rebases the layers above and keeps their approvals when the code did not change. A review change is a commit on the same layer; after it, run `gh stack sync` so the layers above follow. Never merge a layer above an unapproved one. The only PRs that may open beside a lane's stack are a release PR the owner asked for and a PR in another lane.

20. **This is a live consumer app, not a demo** (owner, 30 Oct 2026, says it four times in one morning). Real people sign in with their own phone numbers and order real food that costs real money. The bar is a full production consumer app, the kind the owner names: Swish, Swiggy, Zomato. Not "it works in a test".
    - **Build the path the way a large consumer app builds it**, not the shortest way that passes. Auth, payments and orders get the careful version the first time.
    - **A test double never reaches a customer.** A fixed code, a placeholder sender, a seeded demo row, a token that is "public by design": each one is a loan. Name it in the PR, say when it is repaid, and never let it be the thing a real customer meets.
    - **Dev carries every switch prod carries** (story #797). A feature that is on in prod and off in dev means nobody has really checked it.
    - **An error a customer can see must be true for that customer**, in their own words, with the way out next to it. "This number is already used by another account" shown to the owner of the number is a lie, and lies like it are bugs, not copy nits.
    - **Before a story closes, answer in the PR**: what happens on the hundredth customer, on a bad network, on a second device, and after a week away? No answer means the story is not done.

21. **Maker and checker are never the same session** (owner, 3 Nov 2026: "main chahta ye hun ki ek maker checker process ho. Jo banda build krta hai us cheez ko wahi banda verify na kare. Same with agents."). The session that pushed any commit on a branch does not review, approve or merge that branch.
    - **It holds for every kind of change**: code, documents, boards, records, configuration. The second pair of eyes is about the change, not the file type.
    - **The two sessions are named by their tab**: `goserve-dev` builds, `goserve-qa` reviews and merges. A session that built a branch hands it to the other one and waits. Records the reviewer wants kept are written out for the builder to commit.
    - **Every pull request body carries `Built by: goserve-dev` or `Built by: goserve-qa`**, so a check can later compare it with the session that merges. The gate script is ShipQuick's (feedback #149), not GoServe's.
    - **Both sessions push as `klickbae8yt-star`**, so GitHub cannot tell them apart: this rule is what tells them apart. An approval that says "author and approver were one session" is honest, not allowed.
    - **The one exception** is the owner saying so in that message, written in the pull request as a decision on the record.

22. **How often, really? (owner, 4 Nov 2026, GoServe only, not ShipQuick).** Before any feature, screen or data-model change is proposed, write one line: how often this will happen in the real world with real kitchens, riders and customers (never, once a year, every week, every order), and whether a configuration we already have covers it (another Google account, a setting, a row, a flag). A case that is rare and has an easy configuration is not built; the configuration is written down as the answer. The line goes in the story at Ready, under `Practically:`. Example, 4 Nov 2026: one person working in two kitchens is rare in a pilot of a few kitchens and a second Google account for the second kitchen costs two minutes and keeps the kitchens' emails and alerts apart, so the kitchen chooser and switcher are not built; the error for a Google account already on a kitchen must name that kitchen.

23. **UI mistakes revised before every UI PR (owner, 8 Nov 2026, strict).** Before any PR that touches a screen
    (`app/src/**/*.tsx`, `app/src/**/*.css`, a canvas board), read `docs/UI_MISTAKES.md` fully: the four roots and
    the whole checklist. Fix at the shared rule, never at one call site; sweep every sibling screen and role; run
    the WebKit check for any sheet or form. Write in the PR body `UI mistakes revised: yes · checks <numbers>`.
    No line, no review. Every UI mistake the owner finds is added to that file in the same PR that fixes it, with
    a `docs/LEARNINGS.md` row. The reviewer refuses a UI PR that skipped the file.

24. **Build from the board (owner, 8 Nov 2026: "abhi se rule banao").** A screen is built by looking at its approved board, not from the story text. A human developer keeps the design open beside the code; so do we.
    - **Before code**: render the board at 390x844 and look at it. Read its measurements from the board's markup (x, y, width, height, padding, gap, font, colour of every slip, heading, field, button, chip and row) into a short table.
    - **Port, do not retell**: copy the board's markup and styles into the app. `ink.css` and `app/src/ui/ui.css` are one design system.
    - **After every change**: render the app screen in the board's state and data, put it beside the board at the same scale and full height, and check all four edges. Open no PR until they match. A screenshot baseline is not the reference; the board is.
    - **The PR body shows the board image, the app image and the measurement table.** The reviewer refuses a UI PR without them. A screen with no approved board is not built.

Its `adoption` job fails first, naming the fix, when the pin does not match the submodule or `.pre-commit-config.yaml` has no ShipQuick hooks; `adopt.sh <path> --check` prints the same verdict locally. A child with no caller at all is still caught: `docs/children.md` lists every child, and `scripts/adoption_scan.py` (run daily) opens a `feedback` issue in ShipQuick for one with no caller, or one pinned to a ShipQuick commit over 14 days old. In a child whose caller names a `kit_branch`, the gate files in `scripts/gate_files.txt` (hook config, submodule pin, callers, `.shipquick/` files, `roadmap.json`) live on every code branch too, equal to the kit branch copy: `adopt.sh . --gate-files` puts them there and `--check` fails on a missing or different one (story #479, ADR-017). A hook that cannot start is never skipped with `PRE_COMMIT_ALLOW_NO_CONFIG` or `--allow-missing-config`: stop and tell the reviewer. Full rule: `docs/ADOPTION.md`.
36. **A release freeze is a mechanism, not a sentence** (owner, 30 Oct 2026, from GoServe feedback #126). `scripts/freeze.sh on "<reason>" --until <date>` writes `.shipquick/freeze` on `main` through a PR; `freeze.sh off` removes it the same way; `freeze.sh status` prints what it would decide. While the file exists, `scripts/review_merge.sh` and the `freeze` job in `ci.yml`/`checks.yml` refuse every merge into `main`, except the one PR whose only changed file removes it. Past its `until:` date a freeze does not lift itself — `scripts/check_freeze.py` flags it STALE and still blocks, until someone runs `freeze.sh off` or renews it. Full rule: `docs/PR_RULES.md` section 12.
37. **Harden the gate before enforcing anything new** (owner, 30 Oct 2026, epic #130, story #131). The real gate is CI plus `scripts/review_merge.sh`, and a PR can try to switch both off from inside itself, so three things close that: a check named exactly `gate` (ShipQuick) or `shipquick-checks / gate` (a child) must itself be SUCCESS, not merely absent from a bad-result list; `scripts/protected_paths.txt` lists paths (CI workflows, the ShipQuick pin, lint configs and baselines, token files, other checks' own path lists) a PR can never touch in auto mode — "protected path, owner merges"; the adoption job requires the pinned ShipQuick commit to be merged into `dev`/`main` or tagged, never just existing (`scripts/check_adoption_ancestor.py`); and a disable comment or new ignore-file entry on an added line fails unless the PR names the ADR that justifies it (`scripts/check_disable_comments.py`). Full rule: `docs/PR_RULES.md` section 13. Mode storage (today a local file any agent could write) moves to a cross-checked role system, story #140, not this story.
38. **Library first** (owner, 9 Nov 2026, story #181). Every screen is built only from library components and starts from a template: Jetpack Compose Material 3 on Android and SwiftUI on iOS, used directly, sharing one feel through `design/tokens.json`; `@astryxdesign/core` on the web, used directly, exact version pinned, `astryx doctor --built` failing in CI; Compose Multiplatform is not used. Layout containers are allowed. Hand-drawn UI in app code is refused (Canvas, a custom Shape or ButtonStyle, drawBehind, raw gesture-built controls, M2 or View widgets, and on Android or iOS any third-party UI kit); lint does this from story S7, and until S9 (#187) wires the lint into children, the reviewer checks by hand. If nothing fits, the coder files a `component-request` (`docs/templates/component-request.md`) and stops, with no stand-in built while waiting. The reviewer checks whether existing components can do the job and, if they can, rejects the request and says how; if they cannot, the reviewer asks the owner in one line (the screen, what is missing, why, a picture). On the owner's yes, a reviewer account posts an issue comment `Owner yes: <date> "<his words>"` and adds the label `component-approved`; the issue body never counts, since the coder writes it (story S8, #186, reads exactly that). The coder then builds it in the kit's own library folder (`ui/android/` or `ui/ios/`) with a doc, a contract, a preview, a snapshot, a registry row and a canvas board, and requests its twin on the other platform at the same time; an approved component joins the library and is never built twice. Meta Astryx's agent architecture is copied as code under MIT with its headers kept and the upstream commit recorded, never rewritten, never named "Astryx" as our product. Full rule: `docs/COMPONENT_LIBRARY.md`; decision: `docs/decisions/ADR-012.md`.
39. **Features are flags in one file** (owner, 11 Nov 2026, epic #86). A project records each ShipQuick feature as on or off in `.shipquick/features.json`; the kit lists every feature, its default and its plain words in `scripts/features_default.json`, and one reader, `scripts/features.py`, answers "is this on?". Today only `adopt.sh` reads it (the `pre-commit` and `roadmap` features, and its `--check`); the CI jobs and the scripts read it in stories F4 to F8 of epic #86, and until those land turning any other flag off changes nothing, so nothing is skipped. Only the owner changes a flag, with `! bash scripts/features.sh set <id> on|off`, then a PR he merges: the file is a protected path. When the CI jobs read it (F4) they read it from the base branch, never from the PR under review, and off will mean the owner does more by hand, never that a check is silently skipped. `adoption` and `gate` are locked on. An unknown id or a broken file is an error, never "on". Agents only run `get`. Full rule and the list: `docs/FEATURES.md`; decision: `docs/decisions/ADR-016.md`.
