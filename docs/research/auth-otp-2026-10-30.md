# Phone code login: what the standards actually require (stories #802, #807)

Date of this research: 2026-10-30. Read with [LEARNINGS.md](../LEARNINGS.md) rows of the same date and with
`supabase/migrations/20261027210000_otp.sql`, which is where our rules live.

## How to read the tiers

- **A**: the standard, the law, or the platform saying it about its own product. Good for "this rule exists".
  Not good on its own for "this is right for us".
- **C**: a blog, a vendor page, a comparison article. A Tier C claim alone never changes a decision.
- **S**: our own measurement on our own data. Highest for us.
- Confidence is 0 to 1. Under 0.7 means a test comes before the decision.
- Every source has a motive. A platform's rules tell you what it CAN punish, not what the algorithm does
  or what is good for us.

## The table

| Claim | What the evidence really says | Tier | Confidence | What it changes for us | Source |
|---|---|---|---|---|---|
| SMS as a second factor is "restricted" | NIST SP 800-63B-4 restricts out-of-band authentication over the public telephone network: it may be used, but the risk must be assessed, users must be told, and an alternative must be offered. It is not banned. | A | 0.9 | Our phone code login stays, and Google sign-in is the alternative the clause asks for. The owner's product decision (mandatory phone login, the Swiggy and Zomato pattern) is not in conflict with it. | NIST SP 800-63B-4, out-of-band authenticators |
| A code is at least 6 digits, short lived, single use | Six digits minimum; the validity window should be short, on the order of ten minutes; a code is accepted once. | A | 0.95 | We already do all three: `otp_send_v2` issues six digits with a ten minute expiry, and `otp_verify_v2` sets `consumed_at`. No change. | NIST SP 800-63B-4 |
| **A new code must not reset the failed-attempt count** | Stated almost in those words: generating a new secret must not reset the count of failed attempts against the account. | A | 0.9 | **We break this.** `otp_send_v2` voids the old code on a new send, so the five tries start again on the new row. Five wrong guesses, then a resend, gives five more at no cost. Part of #807. | NIST SP 800-63B-4 |
| Rate limiting should count the caller, not only the target | The throttling guidance is about attempts against an account, and the SMS pumping pattern is about a caller walking many numbers to make a provider's messages bill someone else. | A, C | 0.8 | **We break this too.** Our three sends per ten minutes is per phone number, so one caller can pay three sends against each of a list of numbers. With a real provider that is also our bill. Part of #807. | NIST SP 800-63B-4 (throttling); vendor write-ups on SMS pumping (C) |
| Answers must not reveal whether an account exists | Generic responses and the same status code either way, so a caller cannot tell a registered identifier from an unregistered one. | A | 0.85 | **This is the #807 story.** Our `/otp/send` answers `sign_in: true` for a number that has an account, and before that the 409 `phone_in_use` leaked the same bit on `/otp/verify`. The fix is the server owning both sends and both verifies so the answers are identical. | OWASP Authentication Cheat Sheet |
| SIM change and porting signals should be checked | The guidance says a verifier SHOULD check signals such as a recent SIM swap, a port, or a device change before trusting an SMS code. | A | 0.75 | We check none. Not a story yet; worth one before real money moves through a phone-code-only account. Noted as a follow-up, not scheduled. | NIST SP 800-63B-4 |
| Supabase has no account merge | There is no built-in merge. The documented pattern is to sign in to the account that owns the identifier, then move the other session's rows across. | A | 0.9 | This is exactly what `finishSignIn` plus `/otp/claim` already do, so our shape is the supported one. The problem was never the shape; it was that we spent the code before discovering which path to take. | Supabase Auth documentation |
| Numbers are stored as 91 plus ten digits | Supabase Auth stores a phone without a plus, and keeps a second copy in `auth.identities.identity_data.phone`. | A, S | 0.95 | Measured on our own projects: before the repair every account was stored as bare ten digits, so Supabase's own sign-in could not find any of them. Repaired on dev and on prod; 0 left in either. | Supabase Auth; our own reads of `auth.users` and `auth.identities` (S) |

## What is still a hypothesis

Nothing here was tested by us except the storage format, which we measured. The two breaks we found (the
attempt count resetting on resend, and the per-number rate limit) are read from the standard, not from an
attack we ran. If #807 is built, the acceptance lines in that story are the test.
